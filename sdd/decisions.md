## DEC-07. Итог проекта и план RAG (2026-11-14)

- Итог — чистое окружение: исходные документы + Dockerfile. Разбор, OCR, чанки, индекс, поиск и генерация выполняются только кодом, без внешнего агента и ручной разметки. Конфиденциальные документы не передаются во внешние API, в том числе ассистенту (CASE-07).
- Работа ведётся по `sdd/rag-quality.md` через план `sdd/rag-plan.md`. Улучшения A–H утверждены пользователем («Утвердить»). Из статьи habr.com/ru/articles/1014690 и обзора `deep-research-report (14).md` пользователь поручил выбрать лучшие и оптимальные предложения — отбор в разделах I и J плана.
- Каждый этап включается только по измерению на одинаковых данных без роста ложных ответов (DEC-03).

Источник: ответ технического консультанта, переданный пользователем в сессии 2026-11-13. Закрывает Q-01 (MVP), Q-03 частично (внешние API), Q-07, частично Q-04 и Q-09.

| Тема | Решение консультанта | Что это значит для проекта |
| --- | --- | --- |
| RPS, TTFT, latency, стоимость | Целевых значений нет. Главное — качество поиска, правильность ответов, стабильность. Быстро и недорого — дополнительный плюс | SLA не выдумываем; время ответа измеряем и показываем, но не оптимизируем в ущерб качеству |
| Локальные модели и внешние API | Локальные модели можно, ограничений по архитектуре нет. Внешние API допустимы только для открытых, неконфиденциальных данных. Бюджет на API не задан. Решение должно воспроизводиться по инструкции | По умолчанию всё локально; тексты корпуса наружу не уходят (CASE-07 сохраняется). Любой компонент — с инструкцией офлайн-установки |
| MVP | Сервис: сотрудник спрашивает → находит документы, формирует понятный ответ, показывает источник. Вопрос о порядке действий → последовательность шагов. Нет информации → честно сказать. Метод (BM25, гибрид, agentic RAG) — на усмотрение команды | Q-01: конкурсный MVP. Приоритет — основной сценарий, затем улучшения |
| Самооценка | Баллов сама по себе не даёт, минусом не будет. Можно показать как полезную функцию, если реально контролирует качество или ловит ошибки | Показывать только с измерением: сколько ошибок она ловит на размеченных данных |
| Метрики | Жёсткого набора нет: Recall@k, MRR, nDCG, faithfulness, точность цитирования и др. Важно: правильные документы, отсутствие выдумок, корректные ссылки, подтверждённые измерениями и тестами | Отчёты оценки: Recall@1/3/5, MRR, nDCG@5, ложные ответы, пропущенные факты, ошибки цитирования, правильные отказы |
| Реальная база | Ориентир — предоставленный набор документов; будущий объём не определён. Архитектура должна позволять добавлять документы без переделки. GraphRAG и сложные подходы можно, но более простой подход сопоставимого качества — тоже хорошее решение | Импорт новых документов без ручной перенастройки; никакой привязки к номерам SRC |
| Baseline | Не обязателен; BM25 — нормальная отправная точка. Сравнение со сложным подходом с объяснением прироста полезно, но не обязательно | BM25 фиксируется как базовая линия; гибрид оставляется только при измеренном приросте без роста ложных ответов |
| ML-компоненты | Ограничений нет (NER, BERT, классификация запросов, reranking). Баллы — за результат, не за количество технологий | Каждый компонент — опциональный, с измерением до/после |
| Guardrails и права | Права, изменение/удаление документов, внешние действия не обязательны. Важны обработка ошибок, некорректных запросов, отсутствия информации и противоречий между документами. Сложные функции доступа/действий — только с продуманной безопасностью | Q-05/Q-09: вне MVP. Противоречия между документами — в приоритете |
| Open-source RAG | Допустимы, штрафов нет. Главное — требования кейса, стабильность, умение объяснить архитектуру и показать результат | Выбор стека — по результату. Рекомендация консультанта: сначала закрыть основной сценарий, потом улучшать |
