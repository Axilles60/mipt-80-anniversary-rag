# Обработка документов и модель источников

Статус: производные требования для CASE-T01–T03, CASE-T13. Основание — фактические PDF, DOCX, XLSX из [реестра](../sources/README.md). Это контракт поведения, а не выбор библиотек.

## Требования

| ID | Требование |
| --- | --- |
| DOC-01 | Принимать PDF, DOCX и XLSX. Сохранять оригинальное имя, тип, контрольную сумму и связь извлеченного содержимого с оригиналом. При работе с ZIP игнорировать `__MACOSX`, корректно декодировать имена, не допускать выход путей распаковки за выделенную директорию. ZIP как пользовательский интерфейс загрузки — отдельное решение. |
| DOC-02 | Извлекать заголовки, нумерацию, списки, таблицы, приложения, сноски и связи между ними. Не терять условия и исключения при разделении документа на фрагменты. Пункт с повторным номером идентифицировать также страницей/позицией. |
| DOC-03 | Определять отсутствие, недостаточность или частичность текстового слоя по страницам, сверяя его покрытие с изображением; выполнять OCR сканов, учитывать ориентацию. Сохранять признак OCR и неопределенность. Неразборчивый реквизит не угадывать. Полностью распознанный файл не означает подтвержденную точность каждой цифры. |
| DOC-04 | В XLSX сохранять лист, координаты, подписи строк/столбцов, объединенные ячейки и иерархию; различать значение, формулу и сохраненный результат. Не трактовать пустоту как ноль. Не считать скрытые строки отсутствующими. Не превращать формулу шаблона в утвержденную норму. |
| DOC-05 | В DOCX сохранять строки и ячейки таблиц, колонтитулы и сноски; учитывать встроенные объекты и внешние ссылки, явно отмечать недоступное содержимое. Не ссылаться на выдуманные страницы. PDF цитировать по реальным страницам; XLSX — по листу/диапазону. |
| DOC-06 | Добавлять и переиндексировать документы поддерживаемых форматов через единый процесс без изменения основной логики. Обновление создает новую версию источника и пересматривает связанные отношения; старые ссылки остаются различимыми. Конкретный интерфейс управления — открытое решение. |
| DOC-07 | Повреждение, неподдерживаемый формат, шифрование, ошибка OCR или чтения получают отдельный статус и понятную причину. Ошибка одного источника не останавливает обработку остальных. Частично обработанный документ не показывается как полностью обработанный. |
| DOC-08 | Работать с несколькими документами и длинными текстами без молчаливого отбрасывания значимых приложений/конца документа. Границы длины и стратегия обработки должны быть явными; численные пределы предстоит согласовать. |
| DOC-09 | Сохранять точное содержимое первоисточника отдельно от нормализованного поискового представления. Исправления OCR не должны незаметно менять оригинал. |
| DOC-10 | Выявлять дубликаты и повторно приложенные формы, не считать их независимым подтверждением. Сохранять происхождение обеих копий и отличия при их наличии. |

## Логические сущности

| Сущность | Необходимые сведения |
| --- | --- |
| Документ | ID, название, тип, оригинал, checksum, статус чтения, ограничения доступа/открытости |
| Реквизиты | Номер, дата приказа, дата вступления, период действия/планирования, статус заполненности; каждое значение с основанием |
| Версия и связь | Изменяет, отменяет, приложение к, дублирует, ссылается на; доказательство и неопределенность связи |
| Фрагмент | Текст, родительский раздел, тип содержимого, стабильный локатор, признак OCR, связь с таблицей/приложением |
| Правило | Условие применимости, роль, действие, срок и единица срока, исключение, ответственность, источники |
| Табличные данные | Лист/таблица, строка и столбец, заголовки, иерархия, формула, кеш, замеченные дефекты |
| Ошибка обработки | Источник, этап, причина, масштаб потери содержимого, возможность повторной обработки |

Поля не требуют отдельной базы каждого типа. Физическая схема и способ индексирования будут выбраны после согласования поведения.

## Особенности конкретного корпуса

- SRC-01, SRC-03, SRC-06, SRC-07, SRC-15 содержат сканы; в SRC-15 последние таблицы требуют учета ориентации.
- В SRC-05 и SRC-04 отсутствуют заполненные реквизиты утверждающего приказа. В SRC-03 поля подписей/дат не заполнены. Эти признаки сохраняются в метаданных.
- В SRC-10 есть приказ о вводе функционала, но нет текста упомянутой инструкции. В SRC-05 есть перечень приложений, а не сами формы.
- SRC-12/SRC-18 и SRC-13/SRC-19 повторяют финансовую структуру и формы. Связи не позволяют удвоить доказательную силу.
- В SRC-08 формула F16 содержит `#REF!`, скрытый `IFERROR`. Сохраненный результат не подтверждает исправность формулы.
- Финансовая структура многоколоночная и содержит повторяющиеся подразделения в разных ветках. Поиск должен учитывать финансодержателя и уровень ЦФО.

## Приемка

- AC-DOC-01: для каждого из 21 источника существует запись с оригинальным названием, checksum, статусом и фрагментами либо явной ошибкой.
- AC-DOC-02: из скана находится процедура бронирования зала с привязкой к реальной странице; OCR-сомнение в реквизите сохраняется.
- AC-DOC-03: поврежденная копия файла дает ошибку обработки, остальные документы доступны.
- AC-DOC-04: новая версия регламента загружается без изменения кода; поиск различает версии.
- AC-DOC-05: вопрос по финансовой структуре возвращает путь ЦФО, а не соседнее подразделение из другой колонки.
- AC-DOC-06: пользователь видит, что F16 содержит нарушенную ссылку; система не рассчитывает по ней корректную сумму накладных.
