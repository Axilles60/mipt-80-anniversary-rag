Считаем, что OCR и прочая предобработка выполнена. Считаем, что свели задачу к корпусу текстовых документов

Общая архитектура RAG:

1. Разрезание на чанки. Каждый документ разрезается на чанки. Есть несколько стратегий чанкирования: фиксированный(каждый чанк конкретной длины по токенам), структурный(для документов со структурой: сначала по большим частям, томам, например, далее по главам, а в итоге по страницам, страницу же уже стратегией фиксированного чанкирования), рекурсивный(бьем на чанки по переводам строк, \n, абзацам), файловый(зависящий от файла: таблицы по своему, docx по своему). К каждому чанку добавляется его адрес, на который потом и будет ссылка в ответе. Чанки должны иметь overlap - нахлестывать друг друга по токенам, чтобы смысл на границе не терялся. Parent-child техника: Документ разрезается иерархично от самых больших структурных единиц до чанков, затем при обогащении контекста(добавлении в запрос к генератору) добавляется не просто релевантные чанки, а их родители, содержащие релевантные чанки. Для понимания конкретного устройства способов нарезания на чанки можешь ознакомиться с документацией LangChain

2. Индексирование чанков. Эмбеддинги. Для векторизации используются модели эмбеддингов. Готовые векторы кладутся в векторную базу данных либо просто как численные векторы в некую память. На данном этапе можно применить технику обратного HyDE: для каждого чанка генерируются возможные запросы, на которые чанк был бы релевантным. Затем в отдельное хранилище запросов кладутся эти векторы связанные с чанком

3. Хранилище эмбеддингов. Это должна быть готовая векторная база данных либо ее аналог позволяющий класть новые документы, разрезав их на чанки и получив векторы эмбеддингов чанков. Общая система индексации чанков и хранилища эмбеддингов должны синхронизироваться при добавлении нового документа. Для примера возьмем графовые хранилища: добавление нового документа приведут к созданию новых связей между существующими чанками, новым чанком и старыми. Примеры хранилищ: FAISS, qdrant, HNSW, GraphRAG

4. При поступлении запроса должен выполняться первоначальный guardrail: является ли запрос вопросом по существующей базе документов. Если нет, то наступает финальная генерация ответа, в котором LLM генератор должен вежливо ответить что вопрос не по теме. Если да, то запрос движется по пайплайну RAG дальше

5. LLM генератор должен сделать query rewriting приближая его к возможным документам, которые будут релевантны для этого конкретного пользовательского запроса. Цель query rewriting приблизить эмбеддинг запроса к эмбеддингам документам, так как на смысловом уровне они разделены. Этот query rewriting потребуется для получения более осмысленного эмбеддинга запроса

6. Получение от Encoder модели эмбеддинга query rewriting. Подсчет косинусной близости с представителями хранилища эмбеддингов чанков. Получение top-k наиболее релевантных чанков по алгоритму самого хранилища. Score близости - косинусная близость

7. Получение от исходного пользовательского запроса ближайших к нему по BM25, полнотекстовому поиску. Score близости - BM25

8. Гибридный поиск: RRF со score близости по смыслу от эмбеддингов и конкретному совпадению символов от BM25. Retrieve чанков(либо родителей чанков) происходит по очкам гибридного поиска. Тут получение кандидатов тоже top-k

9. Reranking полученных кандидатов. Через модель reranker: crossencoder либо сам LLM генератор.

10. Полученные top-n где n<k чанки обогащают контекст LLM генератора

11. Этап Prompt Engineering генератора. Системный промпт, обьявление чанков контекста, добавление адреса чанка в цитирование в ответе

12. Финальная генерация ответа LLM генератором. Возможно добавление адресов чанков через детерминированный код

    Это лишь базовая архитектура. Если считаешь нужным, предлагай улучшения, тестируй и выкатывай в прод
