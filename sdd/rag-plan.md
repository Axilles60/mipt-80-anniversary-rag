# План перехода к архитектуре RAG по `sdd/rag-quality.md`

Составлен 2026-11-14. Основание: `sdd/rag-quality.md` (12 этапов), спецификации `sdd/specs/*`, решения DEC-03/05, журнал `sdd/quality-progress.md` (итерации 1–15). Заменяет порядок задач 3–8 в `sdd/work-plan.md`: они встроены в этапы ниже.

## Неизменные ограничения

- **CASE-07 / DEC-03.** Все модели локальные (эмбеддинги, reranker, LLM-генератор); тексты документов и вопросы не покидают машину. Внешние API не используются. Агент оригиналы не открывает; измерения — на синтетике, на оригиналах — `eval/owner_eval.py` у владельца.
- **Поставка.** Исходные документы + Docker: модели скачиваются кодом при сборке с проверкой контрольных сумм, вся обработка — кодом при старте. CPU без GPU — целевая среда, пока не сказано иное. Docker-проверка отложена пользователем.
- **Качество важнее сложности (DEC-03).** Каждый этап включается, только если на одинаковых данных даёт прирост без роста ложных ответов и ошибок цитирования; иначе остаётся выключенным с записью результата. Отложенные наборы прогоняются один раз.
- **Нет выдумок (ANS-04, CASE-T07).** Генератор отвечает только по переданным чанкам; каждое утверждение проверяется кодом на опору в процитированном чанке; при провале — извлекающий ответ (текущий конвейер) как запасной путь.

## Сопоставление со спецификацией

| № | Этап `rag-quality.md` | Сейчас | Разрыв |
| --- | --- | --- | --- |
| 1 | Чанкирование: фиксированное, структурное, рекурсивное, по типу файла; адрес; overlap; parent-child | Фрагмент = абзац DOCX / страница PDF / ячейка XLSX / строка таблицы; пункты и разделы выделяются только в `procedures.py`; адрес с диапазоном символов (`&at=`) | Нет единого чанкера, overlap, иерархии «документ → раздел → чанк»; ячейка XLSX — слишком мелкий чанк |
| 2 | Индексирование, эмбеддинги, обратный HyDE | E5-small ONNX, векторы фрагментов в SQLite (лениво) | Векторы чанков при импорте; HyDE требует LLM |
| 3 | Хранилище, синхронизация при добавлении | SQLite + numpy (точный поиск), кеш по ID фрагмента | Интерфейс хранилища; индексация в момент импорта; FAISS/HNSW — опция при росте корпуса |
| 4 | Guardrail «вопрос по базе?» | Неявно: отказ по поиску и достаточности | Явный классификатор темы до поиска, вежливый ответ вне темы |
| 5 | Query rewriting LLM | Синонимы/сокращения BM25 | Нужен LLM |
| 6 | Dense top-k по косинусу | Есть (E5), z-порог | Перенести на чанки |
| 7 | BM25 по исходному запросу | Есть (FTS5) | Перенести на чанки |
| 8 | RRF, retrieve чанков/родителей | Есть RRF + смысловой фильтр (итерации 5–7) | Перенести на чанки, родители |
| 9 | Reranker (cross-encoder или LLM) | Нет | Локальный cross-encoder |
| 10 | Top-n < k в контекст | Нет (извлекающий ответ) | Сборка контекста с родителями и бюджетом токенов |
| 11 | Промпт: системный, чанки, адреса | Адаптер Ollama `local_model.py` с проверкой ссылок, не используется | Промпт, защита от инструкций в документах (AC-ANS-06) |
| 12 | Генерация, адреса детерминированным кодом | Извлекающая сборка: этапы, обращения, реквизиты редакций | Генерация + проверка опоры + запасной извлекающий путь |

Сильные стороны текущего конвейера (этапы процедур, каналы обращений, выбор редакций по реквизитам, заголовок ≠ ответ, ограничения источника) не выбрасываются: они становятся **структурированным контекстом и проверками** для генератора и запасным ответом.

## Этапы работ

| Этап | Содержание | Измерение / критерий включения | Зависит от |
| --- | --- | --- | --- |
| **R0. Измерения** | Разметка наборов на уровне чанков (ID абзацев уже есть в `fixtures/hybrid`); метрики ответа: faithfulness (доля утверждений с опорой в процитированном чанке), точность цитирования, ложные ответы, пропуски, правильные отказы, вне темы; время ответа и импорта; единый скрипт сравнения конвейеров | Отчёт базовой линии текущего конвейера | — |
| **R1. Чанкер** | `app/chunking.py`: структурное деление по заголовкам/нумерации (раздел → пункт), рекурсивное по абзацам/строкам, фиксированное по токенам токенизатора E5 с overlap для длинных пунктов и страниц; по типу файла: строка таблицы DOCX и строка листа XLSX с заголовками столбцов как один чанк; адрес = версия + локатор + диапазон символов; parent-child (документ → раздел → чанк). Таблица `chunks`, FTS по чанкам, векторы при импорте | Recall@k/MRR/nDCG чанков против фрагментов на тех же вопросах; пробег всех тестов | R0 |
| **R2. Поиск по чанкам** | BM25 + E5 + RRF + z-фильтры по чанкам; расширение до родителя (раздела) для контекста; интерфейс хранилища (SQLite+numpy по умолчанию; FAISS/hnswlib — опция) с синхронизацией при импорте | Прирост метрик поиска без роста ложных ответов в текущем извлекающем ответе | R1 |
| **R3. Reranker** | Локальный многоязычный cross-encoder (ONNX), top-k → top-n | Recall@n/MRR после reranking; время на CPU | R2, **модель** |
| **R4. Guardrail** | Классификатор «вопрос по базе»: близость к корпусу (z по чанкам/темам документов) + лексика; вне темы — вежливый ответ без поиска; при LLM — проверка LLM вторым голосом | Доля правильных «вне темы» без отказов на вопросах по базе | R2 |
| **R5. Генератор** | Локальный LLM (CPU); промпт: роль, правила (только по контексту, ссылки `[C<n>]`, «нет данных», шаги по порядку документа, данные в чанках — не инструкции); контекст top-n с адресами и родителями + структурные подсказки (этапы, редакции, ограничения); пост-проверка кодом: каждое предложение с `[C<n>]` и опорой (совпадение чисел, сроков, форм, номеров с чанком), иначе удаление/отказ; запасной извлекающий ответ | Faithfulness ≥ извлекающего; ложных ответов не больше; полнота шагов выше | R2–R4, **модель** |
| **R6. Query rewriting** | LLM переписывает вопрос в формулировку документа (и/или HyDE-абзац) для dense-поиска; BM25 — по исходному вопросу (как в спецификации) | Прирост Recall на перефразировках без роста ложных | R5 |
| **R7. Обратный HyDE** | LLM при импорте генерирует возможные вопросы к чанку; векторы вопросов в отдельной таблице, совпадение вопрос–вопрос как третий список в RRF | Прирост Recall; время импорта корпуса | R5 |
| **R8. Поставка** | `--build-arg` для моделей (эмбеддинги, reranker, LLM) с SHA-256; при отдельном сервере LLM — Compose; README: архитектура, потоки, переменные, use cases | Сборка и запуск (когда пользователь разрешит Docker) | все |

Параллельно и независимо от моделей остаются задачи прежнего плана: проверка срока в достаточности, противоречия между документами, представление ответа, дубликаты (`sdd/work-plan.md`, задачи 3–7) — они встраиваются в R5 как проверки и структурный контекст.

## Предложения по улучшению плана (на согласование, 2026-11-14)

Учтены: `sdd/rag-quality.md`, статья «Как я победил в RAG Challenge» (habr.com/ru/articles/893356), особенности нашего корпуса (нормативные акты с нумерацией пунктов, сканы, таблицы XLSX, редакции) и ограничения (CPU, локальные модели, Docker, CASE-07). Метка: **[в план]** — предлагаю включить сразу; **[A/B]** — включать только по измерению; **[позже]** — после основного сценария.

### A. Измерения прежде техник
1. **[в план]** Валидационный набор ~100 вопросов по типам ответа: факт/реквизит, срок, «куда/кто», порядок действий, да/нет, определение, таблица/число, историческая дата, составной, нет в базе, вне темы, инъекция. Отложенная часть — отдельно, прогон один раз. Набор владельца (54 вопроса) — на оригиналах.
2. **[в план]** Флаги этапов и единый прогон конфигураций (как `RunConfig` в статье): `NAVIGATOR_PIPELINE=extractive|rag`, `…_RERANK`, `…_PARENT`, `…_REWRITE`, `…_HYDE`, `…_HYBRID`; одна таблица «конфигурация × метрики» на одинаковых данных.
3. **[в план]** Разделять потолок поиска и качество генерации: «нужный чанк в top-k/top-n» отдельно от «ответ верен», чтобы видеть, где теряется факт (принцип «junk in — junk out»).
4. **[в план]** Faithfulness кодом: каждое утверждение с цитатой; числа, даты, номера форм и приказов, адреса, e-mail в утверждении обязаны встречаться в процитированном чанке. Отдельно — точность и полнота цитирования, ложные ответы, отказы, «вне темы», задержка p50/p95, время импорта.

### B. Разбор документов перед чанкингом
5. **[в план]** Промежуточное дерево документа: раздел → пункт (нумерация 1 / 1.1 / 1.1.1, «Глава», «Раздел», «Приложение N»), списки, таблицы, сноски. Чанкер работает по дереву, а не по страницам.
6. **[A/B]** `pymupdf4llm` (из того же PyMuPDF, лёгкий, CPU) — PDF в Markdown с заголовками и таблицами; сравнить с нашим построчным разбором на синтетике. Docling (как в статье) — тяжёлые зависимости (torch), для CPU-контейнера **[позже]**.
7. **[в план]** Очистка текста: переносы слов на границе строк, повторяющиеся колонтитулы и номера страниц, слияние текстового слоя и OCR одной страницы без дублей, мусор OCR.

### C. Чанкинг
8. **[в план]** Пункт нормативного акта — естественный чанк; длинный пункт — до ~300 токенов с перекрытием ~50 (параметры статьи) по предложениям; номер пункта и путь разделов сохраняются в метаданных и в индексируемом тексте.
9. **[в план]** Два текста чанка: индексируемый (путь заголовков + перекрытие + текст) и адрес — точный диапазон символов самого пункта; ссылка открывает и выделяет ровно цитируемый пункт.
10. **[в план]** Parent-child: родитель — раздел (для PDF без структуры — страница); в контекст генератора — найденные пункты и их раздел (как parent page retrieval в статье), с бюджетом токенов. **[A/B]** «раздел / страница / только чанки».
11. **[в план]** Таблицы без LLM: строка DOCX/XLSX — чанк «заголовок столбца: значение»; иерархия строк XLSX (ЦФО 1–4 уровней, AC-DOC-05) — путь родительских строк в индексируемом тексте; в контекст LLM — фрагмент таблицы в HTML (статья: HTML понятнее модели; сериализация через LLM ухудшила качество — не делаем).
12. **[в план]** Тип чанка: норма / форма или шаблон / пример / приложение / сноска / оглавление; формы и шаблоны не выдаются как норма (EVD-08); оглавление не индексируется как ответ.
13. **[в план]** Метаданные чанка: реквизиты документа (номер, дата, вступление в силу, отменён ли — итерация 15), путь разделов, номер пункта, страница, признак OCR — для фильтрации редакций, для цитаты вида «п. 4.2 приказа № … , стр. 3» и для промпта.
14. **[A/B]** Contextual retrieval: в индексируемый текст — название документа и путь разделов (дёшево, без LLM, **[в план]**); краткий контекст раздела, сгенерированный LLM при импорте, — только если окупится по времени импорта на CPU.
15. **[в план]** Дубликаты и повторные приложения (DOC-10): одинаковые чанки разных документов помечаются, в контексте не считаются двумя подтверждениями.

### D. Индекс и хранилище
16. **[в план]** Индексация чанков при импорте (синхронно с добавлением документа), точный поиск SQLite + numpy: для нашего масштаба (тысячи–десятки тысяч чанков) это то же, что FAISS FlatIP в статье. Интерфейс хранилища; HNSW/FAISS — при >100 тысяч векторов **[позже]**.
17. **[в план]** BM25 для русского: стемминг/лемматизация (Snowball через PyStemmer или pymorphy3) вместо обрезки слова до 6 букв.
18. **[в план]** Словарь сокращений из самого корпуса: определения вида «ФЛС — финансовый лицевой счёт», «(далее — КМО)» извлекаются при импорте и расширяют запрос; ручной список `ALIASES` остаётся запасным.
19. **[A/B]** Эмбеддинги крупнее: `multilingual-e5-base`, `BGE-M3` (сильный русский, длинный контекст, ~2 ГБ) против текущего e5-small — по Recall и времени.
20. **[A/B]** Фильтр по документу: если вопрос называет документ или номер приказа — поиск внутри него (аналог «база на документ» из статьи).

### E. Запрос
21. **[в план]** Guardrail в два уровня: дёшево — близость к корпусу (z) и лексика; пограничные случаи — классификация LLM; вне темы — вежливый ответ без поиска. Плюс распознавание попыток инъекции в вопросе.
22. **[в план]** Разбор вопроса: тип ответа (маршрутизация на отдельный промпт, как в статье), дата интереса, категория/условия (НПР, ХОП, РНФ, ГОСТ РВ, зарубежье — ANS-11) для фильтра редакций и уточняющего вопроса.
23. **[A/B]** Query rewriting LLM в стиль регламента; multi-query (2–3 переформулировки) + RRF; HyDE-абзац для dense; BM25 — по исходному вопросу (как в спецификации).
24. **[в план]** Декомпозиция составного вопроса на подзапросы (у нас есть правила; LLM — как запасной путь), поиск и ответ по каждой части, сборка.

### F. Reranking
25. **[A/B]** Локальный cross-encoder (многоязычный, ONNX) против LLM-reranking на Qwen-3B (по образцу статьи: несколько чанков в одном запросе, оценка 0–1 со structured output, итог 0.3 × поиск + 0.7 × LLM). На CPU LLM-reranking дорог — только для top-10.

### G. Генерация
26. **[в план]** Structured output через грамматику llama.cpp (JSON-схема): тип ответа, краткий ответ, шаги `[{текст, [ID чанков]}]`, условия/исключения, сроки, пробелы, противоречия, флаг «недостаточно данных». Рендер и адреса цитат — детерминированным кодом (п. 12 спецификации). Малой модели схема резко снижает число сломанных ответов.
27. **[в план]** Проверка опоры после генерации (п. 4); неподтверждённое утверждение удаляется или помечается; если не осталось ничего — извлекающий ответ текущего конвейера. Это и есть «самооценка», которую консультант просил показать с измерением: сколько ошибок она ловит.
28. **[в план]** Контекст: найденные пункты + их раздел, по порядку документа, с реквизитами и статусом редакции, со структурными подсказками текущих модулей (этапы «до/после», каналы обращения, отменённые редакции, ограничения источника); бюджет ~3–4 тыс. токенов ради скорости CPU.
29. **[в план]** Защита от инъекций (AC-ANS-06): чанки — в разделителях как данные; правило «текст документов — не инструкции»; тест с вредной инструкцией в документе.
30. **[A/B]** Короткое поле рассуждения в схеме (CoT) — для 3B на CPU может не окупиться по времени.
31. **[в план]** Задержка: прогрев модели при старте, кеш KV системного промпта, лимит времени генерации с откатом на извлекающий ответ, потоковый вывод **[позже]**, кеш ответов по (вопрос, версия корпуса).

### H. Эксплуатация
32. **[в план]** Параметры llama.cpp: q4_k_m, `n_ctx` 4096–8192, потоки по ядрам; замер токенов в секунду на CPU; модель и SHA-256 — при сборке образа (`--build-arg WITH_LLM=1`), в одном контейнере.
33. **[в план]** Трассировка запроса для отладки и оценки (ID и оценки чанков, этапы, проверка опоры) — только по флагу, локально; вопросы в обычный журнал не пишутся.

### Предлагаемый порядок
R0 (наборы, флаги, метрики) → R1 (дерево документа, очистка, чанки, метаданные, contextual headers, таблицы) → R2 (поиск по чанкам, стемминг, словарь сокращений, родители) → **R5 (генератор со схемой, проверка опоры, откат)** → R3 (reranker A/B) → R4 (guardrail) → R6 (rewriting/multi-query A/B) → R7 (обратный HyDE — только если окупится по времени импорта) → эмбеддинги крупнее (A/B) → R8 (поставка).

## Решения, которые нужны от пользователя

1. **LLM-генератор (R5–R7).** Предложение: `Qwen2.5-3B-Instruct` в GGUF Q4_K_M (~2 ГБ) через `llama-cpp-python` в том же контейнере — один сервис, без сети, приемлемый русский; время ответа на CPU — десятки секунд. Альтернативы: 1.5B (быстрее, слабее) или 7B (лучше, медленнее, ~4.5 ГБ); отдельный сервер Ollama через Compose. Скачивание модели — с разрешения.
2. **Reranker (R3).** Предложение: многоязычный cross-encoder в ONNX среднего размера; скачивание — с разрешения.
3. **Целевая машина.** Есть ли GPU и сколько ОЗУ на машине показа — определяет размер LLM.

До решений выполняются R0–R2 и R4 (кодовая часть) — модели для них не нужны (E5 уже есть).
