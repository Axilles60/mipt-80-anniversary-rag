## Неизменные ограничения

- **CASE-07 / DEC-03.** Все модели локальные (эмбеддинги, reranker, LLM-генератор); тексты документов и вопросы не покидают машину. Внешние API не используются. Агент оригиналы не открывает; измерения — на синтетике, на оригиналах — `eval/owner_eval.py` у владельца.
- **Поставка (DEC-07).** Итог — чистое окружение: исходные документы + Dockerfile. Модели скачиваются кодом при сборке с проверкой контрольных сумм, вся обработка (разбор, OCR, чанки, индекс, поиск, генерация) — кодом при старте, без внешнего агента и ручной разметки. CPU без GPU — целевая среда, пока не сказано иное. Сборка и запуск образа отложены пользователем (DEC-08): Docker не запускается до отдельного разрешения.
- **Генератор (DEC-06).** `Qwen2.5-3B-Instruct` Q4_K_M через `llama-cpp-python` в том же процессе; Ollama и отдельный сервер не используются. Скачивание других моделей (reranker, NLI, 7B, BGE-M3/FRIDA) — только с разрешения пользователя.
- **Качество важнее сложности (DEC-03).** Каждый этап включается, только если на одинаковых данных даёт прирост без роста ложных ответов и ошибок цитирования; иначе остаётся выключенным с записью результата. Отложенные наборы прогоняются один раз.
- **Нет выдумок (ANS-04, CASE-T07).** Генератор отвечает только по переданным чанкам; каждое утверждение проверяется кодом на опору в процитированном чанке; при провале — извлекающий ответ (текущий конвейер) как запасной путь.

### A. Измерения прежде техник
1. **[в план]** Валидационный набор ~100 вопросов по типам ответа: факт/реквизит, срок, «куда/кто», порядок действий, да/нет, определение, таблица/число, историческая дата, составной, нет в базе, вне темы, инъекция. Отложенная часть — отдельно, прогон один раз. Набор владельца (54 вопроса) — на оригиналах.
2. **[в план]** Флаги этапов и единый прогон конфигураций (как `RunConfig` в статье): `NAVIGATOR_PIPELINE=extractive|rag`, `…_RERANK`, `…_PARENT`, `…_REWRITE`, `…_HYDE`, `…_HYBRID`; одна таблица «конфигурация × метрики» на одинаковых данных.
3. **[в план]** Разделять потолок поиска и качество генерации: «нужный чанк в top-k/top-n» отдельно от «ответ верен», чтобы видеть, где теряется факт (принцип «junk in — junk out»).
4. **[в план]** Faithfulness кодом: каждое утверждение с цитатой; числа, даты, номера форм и приказов, адреса, e-mail в утверждении обязаны встречаться в процитированном чанке. Отдельно — точность и полнота цитирования, ложные ответы, отказы, «вне темы», задержка p50/p95, время импорта.

### B. Разбор документов перед чанкингом
5. **[в план]** Промежуточное дерево документа: раздел → пункт (нумерация 1 / 1.1 / 1.1.1, «Глава», «Раздел», «Приложение N»), списки, таблицы, сноски. Чанкер работает по дереву, а не по страницам.
6. **[A/B]** `pymupdf4llm` (из того же PyMuPDF, лёгкий, CPU) — PDF в Markdown с заголовками и таблицами; сравнить с нашим построчным разбором на синтетике. Docling (как в статье) — тяжёлые зависимости (torch), для CPU-контейнера **[позже]**.
7. **[в план]** Очистка текста: переносы слов на границе строк, повторяющиеся колонтитулы и номера страниц, слияние текстового слоя и OCR одной страницы без дублей, мусор OCR.

### C. Чанкинг
8. **[в план]** Пункт нормативного акта — естественный чанк; длинный пункт — до ~300 токенов с перекрытием ~50 (параметры статьи) по предложениям; номер пункта и путь разделов сохраняются в метаданных и в индексируемом тексте.
9. **[в план]** Два текста чанка: индексируемый (путь заголовков + перекрытие + текст) и адрес — точный диапазон символов самого пункта; ссылка открывает и выделяет ровно цитируемый пункт.
10. **[в план]** Parent-child: родитель — раздел (для PDF без структуры — страница); в контекст генератора — найденные пункты и их раздел (как parent page retrieval в статье), с бюджетом токенов. **[A/B]** «раздел / страница / только чанки».
11. **[в план]** Таблицы без LLM: строка DOCX/XLSX — чанк «заголовок столбца: значение»; иерархия строк XLSX (ЦФО 1–4 уровней, AC-DOC-05) — путь родительских строк в индексируемом тексте; в контекст LLM — фрагмент таблицы в HTML (статья: HTML понятнее модели; сериализация через LLM ухудшила качество — не делаем).
12. **[в план]** Тип чанка: норма / форма или шаблон / пример / приложение / сноска / оглавление; формы и шаблоны не выдаются как норма (EVD-08); оглавление не индексируется как ответ.
13. **[в план]** Метаданные чанка: реквизиты документа (номер, дата, вступление в силу, отменён ли — итерация 15), путь разделов, номер пункта, страница, признак OCR — для фильтрации редакций, для цитаты вида «п. 4.2 приказа № … , стр. 3» и для промпта.
14. **[A/B]** Contextual retrieval: в индексируемый текст — название документа и путь разделов (дёшево, без LLM, **[в план]**); краткий контекст раздела, сгенерированный LLM при импорте, — только если окупится по времени импорта на CPU.
15. **[в план]** Дубликаты и повторные приложения (DOC-10): одинаковые чанки разных документов помечаются, в контексте не считаются двумя подтверждениями.

### D. Индекс и хранилище
16. **[в план]** Индексация чанков при импорте (синхронно с добавлением документа), точный поиск SQLite + numpy: для нашего масштаба (тысячи–десятки тысяч чанков) это то же, что FAISS FlatIP в статье. Интерфейс хранилища; HNSW/FAISS — при >100 тысяч векторов **[позже]**.
17. **[в план]** BM25 для русского: стемминг/лемматизация (Snowball через PyStemmer или pymorphy3) вместо обрезки слова до 6 букв.
18. **[в план]** Словарь сокращений из самого корпуса: определения вида «ФЛС — финансовый лицевой счёт», «(далее — КМО)» извлекаются при импорте и расширяют запрос; ручной список `ALIASES` остаётся запасным.
19. **[A/B]** Эмбеддинги крупнее: `multilingual-e5-base`, `BGE-M3` (сильный русский, длинный контекст, ~2 ГБ) против текущего e5-small — по Recall и времени.
20. **[A/B]** Фильтр по документу: если вопрос называет документ или номер приказа — поиск внутри него (аналог «база на документ» из статьи).

### E. Запрос
21. **[в план]** Guardrail в два уровня: дёшево — близость к корпусу (z) и лексика; пограничные случаи — классификация LLM; вне темы — вежливый ответ без поиска. Плюс распознавание попыток инъекции в вопросе.
22. **[в план]** Разбор вопроса: тип ответа (маршрутизация на отдельный промпт, как в статье), дата интереса, категория/условия (НПР, ХОП, РНФ, ГОСТ РВ, зарубежье — ANS-11) для фильтра редакций и уточняющего вопроса.
23. **[A/B]** Query rewriting LLM в стиль регламента; multi-query (2–3 переформулировки) + RRF; HyDE-абзац для dense; BM25 — по исходному вопросу (как в спецификации).
24. **[в план]** Декомпозиция составного вопроса на подзапросы (у нас есть правила; LLM — как запасной путь), поиск и ответ по каждой части, сборка.

### F. Reranking
25. **[A/B]** Локальный cross-encoder (многоязычный, ONNX) против LLM-reranking на Qwen-3B (по образцу статьи: несколько чанков в одном запросе, оценка 0–1 со structured output, итог 0.3 × поиск + 0.7 × LLM). На CPU LLM-reranking дорог — только для top-10.

### G. Генерация
26. **[в план]** Structured output через грамматику llama.cpp (JSON-схема): тип ответа, краткий ответ, шаги `[{текст, [ID чанков]}]`, условия/исключения, сроки, пробелы, противоречия, флаг «недостаточно данных». Рендер и адреса цитат — детерминированным кодом (п. 12 спецификации). Малой модели схема резко снижает число сломанных ответов.
27. **[в план]** Проверка опоры после генерации (п. 4); неподтверждённое утверждение удаляется или помечается; если не осталось ничего — извлекающий ответ текущего конвейера. Это и есть «самооценка», которую консультант просил показать с измерением: сколько ошибок она ловит.
28. **[в план]** Контекст: найденные пункты + их раздел, по порядку документа, с реквизитами и статусом редакции, со структурными подсказками текущих модулей (этапы «до/после», каналы обращения, отменённые редакции, ограничения источника); бюджет ~3–4 тыс. токенов ради скорости CPU.
29. **[в план]** Защита от инъекций (AC-ANS-06): чанки — в разделителях как данные; правило «текст документов — не инструкции»; тест с вредной инструкцией в документе.
30. **[A/B]** Короткое поле рассуждения в схеме (CoT) — для 3B на CPU может не окупиться по времени.
31. **[в план]** Задержка: прогрев модели при старте, кеш KV системного промпта, лимит времени генерации с откатом на извлекающий ответ, потоковый вывод **[позже]**, кеш ответов по (вопрос, версия корпуса).

### I. Дополнения по статье habr.com/ru/articles/1014690 (Agentic RAG Legal Challenge, 2026)

34. **[в план]** Grounding как главная метрика: верный ответ со ссылкой не на тот пункт/страницу считается ошибкой (у авторов именно рост grounding 0.45→0.90 поднял итог). В R0 — отдельная метрика «процитирован ожидаемый пункт».
35. **[в план]** «Pinning» реквизитов: в контекст генератора добавлять заголовочный чанк (название, номер, дата, вступление в силу) каждого документа, чьи пункты попали в контекст, и документа, названного в вопросе.
36. **[A/B]** Агентный цикл достаточности: после первого ответа модель (поле схемы `need_more`) формулирует уточняющий запрос → ещё один раунд поиска (не более 1–2) → ответ. На CPU — только если вопрос остался без опоры.
37. **[A/B]** Reasoning по типу вопроса: короткое поле рассуждения включать для да/нет и «кто/какой» (у авторов без него −8–16%), выключать для дат, чисел, сроков.
38. **[в план]** Контроль длины чанка под лимит эмбеддера (E5/FRIDA — 512 токенов, лишнее обрезается молча): считать токены настоящим токенизатором, тест на отсутствие обрезки.
39. **[A/B]** FRIDA (RU/EN, поддерживает префиксы) как кандидат эмбеддера наряду с BGE-M3; разреженный (sparse) поиск вместо/вместе с BM25 — сравнить.
40. **[A/B]** LLM-реранкер, выбирающий номера полезных чанков (а не оценки), — дешевле по токенам для 3B на CPU; сравнить с cross-encoder.
41. **[позже]** Контекстуализация чанков LLM (чанк + весь документ) — у авторов 15–20 с на чанк локально; для CPU и Qwen-3B непрактично на всём корпусе; возможна на уровне раздела.
42. **[в план]** Цикл анализа ошибок: просмотрщик результатов оценки (HTML-отчёт: вопрос, ожидание, ответ, цитаты, где потерян факт), правки промпта по группам ошибок с перепроверкой на отложенном наборе.

### J. Отбор из обзора `deep-research-report (14).md` (2026-11-14)

Критерий отбора: польза для корпуса в ~20 документов на русском при CPU, локальных моделях и Docker; цена — задержка, размер образа, сложность. Обзор сам делает вывод: на малом корпусе простая база (FTS5 BM25 + небольшой генератор) даёт 80–90 % лучшего результата, экзотика — малый прирост.

**Принято**
43. **[A/B]** Перекрытие чанков: обзор приводит свежие данные «перекрытие не даёт прироста recall». У нас оно только в индексируемом тексте — сравнить «с/без» и размер 300/500 токенов на tuning; оставить то, что лучше или проще при равенстве.
44. **[в план]** Дедупликация близких чанков в контексте (хеш нормализованного текста) — дёшево, снижает шум и двойной счёт подтверждений (DOC-10).
45. **[A/B]** Порядок контекста: «сильнейшие первыми» против «порядок документа» (эффект «lost in the middle» у малых моделей); окно ±1 соседний пункт против всего раздела.
46. **[A/B]** Проверка утверждений многоязычной NLI-моделью (CPU, ~0.3B, например mDeBERTa XNLI) поверх текущей кодовой проверки: метрика — сколько неподтверждённых утверждений ловит дополнительно и сколько верных ошибочно отбрасывает. Скачивание — с разрешения.
47. **[в план]** Отказ по уверенности поиска: порог по лучшей z-оценке/BM25 для «нет данных» до вызова LLM — экономит время CPU и снижает выдумки на вопросах вне базы; калибровка на tuning.
48. **[в план]** Контрольная конфигурация «без контекста» (closed-book) в `measure_rag`: насколько генератор выдумывает без документов — для защиты и для калибровки проверки опоры.
49. **[в план]** Метрики claim-level: доля утверждений с подтверждающей цитатой (citation precision/recall на уровне утверждений), точность «нет ответа» — дополняют уже введённые grounding и неподтверждённые утверждения.
50. **[A/B, позже]** Генератор 7–8B (Qwen2.5-7B Q4, ~4.7 ГБ) — обзор рекомендует ≥7B для развёрнутых ответов; на CPU в 2–3 раза медленнее; только если 3B не справится по метрикам. Скачивание — с разрешения.
51. **[A/B, позже]** BGE-M3 вместо E5-small — совпадает с п. 19; Doc2Query (обратный HyDE) — один раз при импорте, для 20 документов приемлемо по времени, оставлен в R7.

**Отклонено для наших условий:** ColBERT/multi-vector (×10 к хранению, нужен GPU), сравнение внешних векторных БД (Qdrant, Milvus, pgvector — на десятках тысяч чанков разница меньше миллисекунды, а SQLite уже даёт синхронизацию и транзакции), Docling/Marker (6–90 с на страницу), семантический и пропозиционный чанкинг (медленно, требует LLM на индексацию, без явного выигрыша), late chunking/RAPTOR (сложность), GPU-конфигурации 8–24 ГБ (целевая среда — CPU), Ollama (уже выбран llama.cpp в процессе), PaddleOCR (OCR вне рамок `rag-quality.md`; Tesseract уже настроен).
